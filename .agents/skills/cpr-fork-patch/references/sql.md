# Fork SQL 约束

fork 每次在新的上游发行上重放补丁，数据库却保留实际执行过的迁移与数据
SQL 设计必须同时兼容新建数据库和已运行旧 fork 的数据库，不能以 Git 重放代替数据库升级
通用迁移登记、冻结检查和测试环境见[数据库迁移](../../../../backend/migrations/README.md)

## 编号与冻结

- fork migration 使用 `9001`–`9999`，在所有补丁主题间全局分配；创建前核对当前文件及已发布 fork 的清单，不复用已分配编号
- 上游 migration 的编号、文件名和字节保持对应原始上游 tag 的内容，不为 fork 重新编号、修改或删除
- 已发布或已执行的 fork migration 同样冻结编号、文件名和字节；后续变更追加新编号，源文件持续保留，即使相应功能不再使用或已被上游吸收
- 按迁移文档登记 `.frozen-sha256`；不能删除、改写 `_sqlx_migrations` 或 checksum 来绕过校验

保留编号只防止版本重复，不保证 schema 独立；若上游进入保留区间或已分配编号发生冲突，先报告，不能自行重排已发布编号

## 对象所有权

fork 创建的表、索引、约束、序列、函数等具名对象统一使用 `fork_` 前缀，避免占用上游命名
后续 migration 可以改变 fork 自有对象，但必须保留支持升级所需的数据与功能合同

- 不修改或删除上游已有的表、列、索引、约束、函数及其他 schema 对象，也不向上游表增加列或约束
- 不在 fork migration 中更新、回填或删除上游业务数据
- 不建立从 fork 对象到上游对象的 schema 依赖，包括跨边界的外键 `REFERENCES`、trigger、view 和依赖上游对象的函数；移除 `ON DELETE CASCADE` 仍保留外键依赖
- 不让上游 migration 必须等待某个 fork migration 才能执行；高编号不意味着 fork 对象总是在未来的低编号上游 migration 之后才出现

业务代码可以读取上游对象，把 fork 自有状态写入 fork 对象
读取字段、身份关联和生命周期仍构成应用依赖，须在移植时核对；无外键不等于没有业务关联

## 身份与生命周期

使用上游账号或其他实体的 ID 关联 fork 数据时，先明确删除、重建和身份变更的合同
账号数量少或数据可重新获取，不能替代明确的清理保证

- 所属功能应说明孤儿数据何时清理、触发条件、失败处理，以及没有后续触发时是否允许残留
- 读取按稳定身份与实体世代隔离，检查并发删除和 ID 复用，避免旧实体的数据被新实体继承
- 写入防止基于过期凭据、身份或观测时间的晚响应覆盖当前状态；同身份凭据轮换后的快照有效性由功能合同决定
- 使用事务或锁时，说明它保护的状态与生命周期，不把已取消的外键保证隐含转交给调用方

这些保证写入所属 [API](../../../../docs/api.md) 或[架构](../../../../docs/architecture.md)章节，并用真实数据库路径验证；本参考不规定所有功能使用相同的清理策略

## 升级验证与异常处理

新增 SQL 或升级上游时，至少验证两条实际迁移路径：

1. 新建数据库：执行目标上游 migration，再执行当前 fork migration
2. 旧 fork 数据库：保留旧上游与 fork 已应用的 migration 和数据，再执行新增上游及 fork migration

第二条路径中，高编号 fork migration 可能早已执行，新出现的低编号上游 migration 随后执行
核对实际 ledger、重启初始化、数据保留和本主题生命周期行为，不能只验证新库或只通过构建

发现已发布或已执行的不合规 migration 时，先核实受影响版本、数据库执行记录和实际 schema，区分已确认范围与未知使用者
按维护指南报告冲突、影响、支持的升级来源及可选处理，等待维护者明确决定
此前已针对该迁移冲突、受影响数据库范围和具体处理动作作出明确决定的，依决定执行；通用升级或发布授权不能代替这项决定
不得默认通过撤回发行、直接改编号或通用启动桥接绕过冻结规则，也不能假定某个生产实例尚未执行就代表所有数据库都未执行
